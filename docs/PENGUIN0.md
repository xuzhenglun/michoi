# PENGUIN0 室内门禁协议技术说明

本文档描述 `pad.cap` 中可以直接验证的事实，以及用软件门口机模拟器（`emit-door`）
对真实 Pad 交互后确认的行为（下称“实机验证”）。名称是便于实现而取的中性名称，
并非厂商公开名称。标为“推测”的字段需要更多抓包确认。

## 1. 捕获对象与传输

两个抓包：`pad.cap` 是一次门口机→Pad 的呼入；`call-door.cap` 是 Pad 主动向外
（查看多台入口门摄像头、并呼叫电梯）。文档中的真实 station ID 用占位符表示。

| 角色 | 占位 ID | 命名规律（真实 ID 编码的信息） | IPv4 |
|---|---|---|---|
| 室内 Pad（本机） | `S00000000000` | `S` + 楼盘 + 楼层 + 房号 | `192.168.124.61` |
| 入口门 1/2/3 | `M…01/02/03000` | `M` + 楼盘 + 入口序号 + `000` | `192.168.124.2/.3/.4` |
| 入口门 4/5/6 | `M…04/05/06000` | 同上，其他楼栋/区段 | 本子网外 |
| 门铃 | `L…111031…036` | `L` + 楼盘 + 楼层 + 单元 | 本子网外 |
| 楼宇网关 | — | 跨楼栋骨干 | `192.168.120.2` |

站点身份由 ID 决定：前缀区分类型（`M` 入口门、`L` 门铃、`S` 室内 Pad），其后编码
楼盘/楼层/单元。**同类设备（如全部入口门）只因所在网段不同而可达性不同**，不是两种
设备。

- UDP 10008：设备发现（“谁是这个 ID”），载荷没有 `PENGUIN0` 公共头。
- UDP 10000：bootstrap、通话控制、监控、JPEG、PCM、通话后快照、电梯。
- 除嵌入的 IPv4 地址使用网络字节序外，多字节整数均为 little-endian。
- pcap 在 Linux bridge 上抓取，包含 UDP GRO 合并记录；真实 socket 通常仍一次收到
  一个 UDP datagram。解析器必须能按逻辑长度和下一个 magic 拆分。
- `call-door.cap` 2831 个包已全部归类，无未知包。

## 3. 发现与 bootstrap

### UDP 10008

- Request：byte 0 为 `01`，后接 NUL 结尾/填充的房间 Station ID。
- Reply：byte 0 为 `02`，后接固定 34 字节、NUL 填充的房间 Station ID。

### `0098/02` bootstrap reply

Body：

| Offset（body） | Size | 说明 |
|---:|---:|---|
| 0 | 2 | `01 00` |
| 2 | 20 | Pad Station ID，NUL 填充 |
| 22 | 4 | Pad IPv4 |
| 26 | 840 | 当前捕获中全 0 |

总长 898。门口机 request 的 declared length 为 20、实际只有 32 字节；实现按实际 UDP
边界接收，不按该 declared length 截断公共头。

### `005d/01` 呼叫寻呼（振铃触发）

门口机在建立会话前，先向 Pad 连发 `005d/01`，实机验证确认这是让 Pad **进入来电、
开始本地振铃**的触发包，而非单纯的周期状态。

- Body 固定 4 字节 `00 1e 00 00`：offset 1 的 `0x1e = 30` 是**接听超时秒数**，Pad
  据此在来电界面本地倒计时 30→0，数完无人接听即结束。捕获中 10 个寻呼包该值恒定；
  它是超时通告，与实时流长度无关。
- 捕获中门口机每 100 ms 发一个，共约 10 个（约 1 秒）。寻呼停止后，Pad 依靠已建立
  的会话保持振铃，直到接听或超时；无需持续重发寻呼。
- Body 不含任何设备 ID，是与端点无关的固定字节。

### 呼叫建立顺序

实机验证的完整建立顺序（缺少寻呼阶段时，Pad 会接受媒体会话但**不振铃**）：

```text
门口机→Pad  005d/01   ×10（每 100 ms，振铃触发）
门口机→Pad  0098/01        （bootstrap request）
Pad→门口机  0098/02        （bootstrap reply）
门口机→Pad  00b7/01   ×3   （session setup）
Pad→门口机  00b7/03        （capability reply）
门口机→Pad  00b7/0a(JPEG)  （振铃期间即开始，来电界面显示门口画面）
```

## 4. Session family `0x00b7`

Session body 前 48 字节是两个 endpoint：

| 绝对 offset | Size | 说明 |
|---:|---:|---|
| 32 | 20 | 门口机 Station ID |
| 52 | 4 | 门口机 IPv4 |
| 56 | 20 | Pad Station ID |
| 76 | 4 | Pad IPv4 |

Pad 发出的 answer、unlock、keepalive、hangup 都是相同的 80 字节 envelope，只改变
opcode。捕获中用户称按了两次开锁，但只出现一个有效 `00b7/06`；实现因此对一次上层
Unlock 只发一个 datagram，并做一秒防抖。

### setup capability

门口机 `00b7/01` 在 endpoint 后携带 `VIDEOA` 及一组能力值。Pad 的 96 字节 reply 为：

```text
endpoint block (48)
"VIDEOA\0\0" (8)
u16le: 50, 9, 9, 255
```

这些数值的厂商含义尚未证实；兼容实现逐字节复用。

## 5. Media `00b7/0a`

Media header 位于绝对 offset 80，共 10 字节：

| Offset | Size | 类型 | 说明 |
|---:|---:|---|---|
| 80 | 2 | u16le | media type |
| 82 | 2 | u16le | frame/packet sequence |
| 84 | 2 | u16le | fragment count |
| 86 | 2 | u16le | 1-based fragment index |
| 88 | 2 | u16le | 本 slot 有效字节数 |
| 90 | ... | bytes | media payload |

### JPEG（type 1）

- UDP 逻辑长度固定 1290：80-byte envelope + 10-byte media header + 1200-byte slot。
- 一帧通常分 7 片；最后一片只取 `valid_length`，不得拼接 padding。
- 按 sequence 聚合，可容忍乱序；所有 1..N 片存在后拼接。
- 完整帧以 `ffd8` 开始、`ffd9` 结束。
- 捕获得到 230 帧，640×480 JFIF，45.061173s 至 54.129880s，约 25 FPS。

### Audio（type 3）

- 逻辑长度固定 602：80 + 10 + 512。
- PCM 为 mono、8 kHz、signed 16-bit little-endian。
- 每包 256 samples，即 32 ms。
- 门口机→Pad 的 declared length 为 0；Pad→门口机为 602。
- 双向音频从 50.924707s 开始，Pad 接听后约 0.99 秒出现。

**振铃期间不得发送音频。** 捕获中门口机音频严格在 Pad answer（`00b7/05`，
49.933s）之后才出现（50.925s）；振铃阶段只发 JPEG（首帧 45.061s）。实机验证：
若在振铃期就发送音频（哪怕是静音包），Pad 会认为语音通道已打开、直接进入“通话中”，
**不再播放本地铃声**。因此门口机实现必须在收到 `00b7/05` 后才开始发音频。

## 6. 捕获时序

| 时间 | Frame | 事件 |
|---:|---:|---|
| 42.150088 | 2 | 房间 discovery |
| 42.159 起 | — | `005d/01` 呼叫寻呼 ×10（每 100 ms，振铃触发） |
| 43.162706 | 14 | bootstrap request |
| 43.164778 | 15 | bootstrap reply |
| 43.179387 | 18 | 首次 session request |
| 43.326102 | 21 | Pad capability reply |
| 45.061173 | 43 | 首个完整 JPEG |
| 49.933180 | 919 | Pad answer |
| 50.924707 | 1111 | 双向 audio 开始 |
| 51.559897 | 1296 | unlock |
| 54.090359 | 1985 | Pad hangup |
| 54.091538 | 1986-1988 | 门口机重复 hangup |
| 54.097089 | 1992 | post-call snapshot 开始 |

状态机：

```text
Idle --005d/01(+0098/01,00b7/01)--> Ringing --00b7/05--> Connected
  ^          (振铃+视频，无音频)        |                     |
  +--------------1e--------------------+---------1e----------+
                                                            +--06--> Connected
```

`005d/01` 寻呼使 Pad 进入 Ringing；`0098/01`、`00b7/01` 在振铃期间建立媒体会话，
门口机同时推送 JPEG 但**不发音频**（否则 Pad 不振铃，见 §5）。门口机没有对 `05`
单独回复；它通过在收到 `05` 后开始发送音频来体现接听状态。因此物理
Pad 与远端客户端的 first-answer-wins 必须在桥上集中观察/仲裁，不能靠两个独立客户端
自行判断。

## 7. 快照 family `0x009b` / `0x00b4`

捕获中的文件信息包含：

- path：`/bffs1`
- filename：`cap0904004745.jpeg`
- station：`M00000000000`

`00b4/04` 使用约 1200 字节数据 slot，共 26 个数据消息。`00b4/01` 为文件请求，
`02` 返回长度/分片信息，`03` 开始，`04` 数据，`05` 为接收确认（具体字段语义仍需
更多样本验证）。该传输不参与实时画面，首版只解析、记录，不主动发起。

## 8. Pad 主动侧：枚举、监控、按 ID 呼叫、电梯

来自 `call-door.cap`(Pad `.61` 主动访问 6 入口门 + 6 门铃,楼下入口门 `.3` 在第
2/3 次成功看到画面和声音;最后成功呼叫电梯到本层)。

### 设备枚举 —— 名单是预置/推导的，不是网络扫描

Pad **不通过网络发现**可访问的设备,它按一份**预置或由 ID 命名规则推出的名单**逐个
探测。抓包证据:所有 UDP 10008 查询都是**按具体 ID 广播**(不是通配枚举):

| 查询的 ID（占位） | 含义 | 结果 |
|---|---|---|
| `M…01/02/03000` | 本子网入口门 1/2/3 | `.2/.3/.4` 应答 → 可 `00b8` 直接看 |
| `M…04/05/06000` | 入口门 4/5/6(本子网外) | 10008 无应答 → 转 `008c` 网关,仍无应答 |
| `L…111031…036` | 本楼层 6 个门铃 | 无应答 |
| `S…122010` | 另一台 Pad(呼叫其他 Pad) | — |

即:名单来自装机下发或按 `类型+楼盘+楼层+单元` 规则生成;Pad 对名单里每个 ID 发
10008“你在吗”,同子网者应答、可看,跨网段者交给网关。整个抓包里**没有 TCP、没有
名单下载协议、没有通配枚举**。实现“可看摄像头列表”应由配置的名单 + 10008 探测得出,
而非期待协议提供发现。

### monitor —— 与呼入本质对等

**主动查看摄像头是呼入的镜像**:同样的 32 字节头、同样的 48 字节端点块、同样的
`0a` 媒体帧(JPEG type 1 / 音频 type 3,媒体头在 offset 80)、`0c` keepalive、
`1e` 结束、`03` 能力应答。差别只有三点:

- 家族号 `0x00b8`(呼入是 `0x00b7`);
- 发起方是 Pad,端点块顺序是 **[发起方 | 目标]**(呼入是 [门口机 | 房间],即也是
  [发起方 | 目标],只是发起方恰为门口机);
- 没有 `05`/`06`(接听/开门)——查看是只读的,不"接听";门口机多发一个 `0f`
  表示媒体就绪。

时序(成功的 `.3`):Pad 发 `00b8/01` → 门口机回 `00b8/03`(×3)+`0f` → 门口机
持续推 `00b8/0a` 音频,随后音视频 → Pad 每秒 `00b8/0c` keepalive → Pad 发
`00b8/1e` 结束。`monitor_request` 有"合成==抓包"单测。因此实现上监控与呼入共用
封装、端点块、媒体框架和 JPEG 重组,只是家族号与发起方向不同。

门口机→Pad 还有一个 `00b8/02`(抓包里 1 个,来自 `.2`):140 字节,body 内在
offset 90 **嵌套了原始的 `00b8/01` 请求**,是监控的**否定/重定向式应答**(该门口机
未授予画面,把请求回带);成功路径是 `00b8/03`。我们只观察它,不发送。

### 008c —— 按 ID 经网关呼叫本子网外的设备

入口门都是同一类设备,区别只在网段可达性:名单里落在本子网的(1/2/3)用 10008 直接
找到;落在本子网外的(入口门 4/5/6、门铃),10008 广播到不了,Pad 改向**楼宇骨干
网关** `192.168.120.2` 发 `008c/01`,端点块为 [本房间 | 目标(IP 置 0,仅凭 ID)]。
抓包里对 `M…04/05/06000` 和 `L…111031…036` 各试 10 次均无应答(跨网段需网关侧
路由/权限)。本仓库暂不主动实现 008c,仅解析记录。

### 拨出呼叫（Pad→Pad，`call.cap`）

Pad 主动拨号另一台设备(语音+视频)。与门口机呼入不同:**没有 `005d` 振铃**,改为
`0098/01`(引导,declared=32)→ `00b7/0d`(呼叫建立/邀请,端点块 + 2 字节 `01 00`,
也发往楼宇网关用于路由)→ `00b7/01`(能力 `VIDEOA 01 00…`,256 字节,`CALL_REQUEST_CAPABILITY`)
×3。端点块顺序 **[主叫 | 被叫]**。被叫接听发 `00b7/05`,随后双向 `00b7/0a`
音视频(与呼入同一媒体框架),`00b7/0c` keepalive,`00b7/1e` 挂断。主叫在收到 `05`
后才发媒体。`call_request`/`call_setup` 有“合成==抓包”单测。

### 0106 电梯呼叫

`0106/01` Pad→门口机(`.2`),载荷只有房间 station ID(IP 在线上置 0),declared=32,
实际 74 字节;门口机回 `0106/02`(32 字节,仅头)确认。**楼层由房间 ID 推出**,请求
本身不带楼层。`elevator_request` 有"合成==抓包"单测。

## 9. 安全与实现约束

- 只接受配置的 station ID、IP 和 MAC；任何值均不得仅依赖 UDP 源地址认证。
- 未处于远端已接听且 owner 为 remote 时，不得发送真实 unlock。
- 一个上层 command ID 只能执行一次，重连重试返回缓存结果。
- bridge/NFQUEUE 故障必须 fail-open，保证原 Pad 在程序退出后恢复。
- 文档与实现仅用于用户获授权的自有门禁网络。
